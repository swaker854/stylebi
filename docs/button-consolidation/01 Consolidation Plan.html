Button Consolidation Plan

A short, actionable plan to collapse the 5 shipped button classes into 3 emphasis tiers + 2 modifiers, per §5 of the Button Decision Table. Token fixes resolve the §4 flags. Mechanical renames are codemod-safe; the cases that need a human are listed explicitly at the end.

Do this in the stylesheet before the codemod, so renamed call-sites land on correct visuals.

4 · The enumeration script (the foundation)

Before any consolidation, one script walks the codebase and dumps every button call-site to a table. It is the single artifact the rest of the plan leans on — write it once, use it three times.

What it doesDetail
ScansAll *.component.html templates under web/projects/portal + shared. Must catch dynamic forms too — [class.btn-primary], [ngClass], and classes assembled in .ts — not just static class="…". (This is why grep alone isn't enough; use an Angular-aware / AST parse.)
RecordsPer call-site: file, line, current variant class, surrounding context (dialog footer / header / toolbar / row), and sibling button variants in the same container.
FlagsDerived columns the §2 rules can assert on — e.g. 2+ primaries in one footer, danger present, dismiss-variant ≠ canonical.

It earns its keep three times over: (1) it's the complete inventory design works from in §6; (2) its flag logic is the lint rule in §5 step 5; (3) re-running it after the codemod proves the migration is complete. Build it first — it's the most parallel-safe task and blocks nothing.

5 · Sequence

  1. Build the enumeration script Dev

    §4. Parallel-safe, depends on nothing. Produces the full call-site inventory design needs and the flag logic the lint rule reuses.

  2. Land the CSS/token changes Dev

    §3, behind the existing class names. No call-site touched yet; visuals for ghost/danger/icon become correct.

  3. Run the safe codemod Dev

    The three mechanical rows in §2: btn-light → btn-secondary, btn-default → btn-ghost, btn-light-no-bg → btn-ghost. One PR, fully reversible.

  4. Resolve the judgment cases Design + Dev

    Work the §6 list against the script's inventory: every footer with 2+ primaries, every .btn-danger, every Cancel variant. Each gets a decided variant + reason.

  5. Add the lint rule Dev

    Encode the §2 rules as an ESLint/template check so violations can't return — built directly on the §4 script's flag logic.

6 · Decisions needed from design (the non-mechanical part)

These cannot be codemod'd — they need an intent call before code:

  • Two-primary footers. e.g. image-format-select ships SVG + PNG both as .btn-primary. Decide: one primary + one secondary (PNG has defaultFocus), or both neutral. Then sweep for every other 2+-primary footer.
  • Cancel / dismiss variant. Table §2 says dismiss = .btn-default (→ .btn-ghost), but real dialogs mix in .btn-secondary (e.g. image-format-select). Pick one canonical dismiss variant and apply everywhere.
  • Danger split. For each .btn-danger site: is it a destructive CTA (.btn-primary.is-danger) or an inline/row action (.btn-ghost.is-danger)?
  • Secondary budget. Confirm the rule "Secondary only when it stands above its neighbours" — otherwise supporting actions default to Ghost.
